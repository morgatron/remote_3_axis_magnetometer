# Secrets Management & System Security Guide

This guide outlines security practices and secret-storage strategies across all tiers of the **Remote 3-Axis Magnetometer Acquisition System**, covering:
1. **Central Server Secrets (`API_KEY`)**
2. **Cloudflare Tunnel Tokens (`cloudflared`)**
3. **Remote Edge Gateways (`gateway.py`)**
4. **Embedded Microcontrollers (ESP32 Sensor Nodes & Receivers)**
5. **Git Hygiene & Leak Prevention**

---

## 1. Central Server Secrets (`API_KEY`)

The central data server uses an `API_KEY` to authenticate data-mutating requests (`POST /api/v1/telemetry`, `POST /api/v1/nodes/update`) while keeping dashboard reads open to authorized users.

### Best Practices:

1. **Generate High-Entropy Cryptographic Keys**:
   Avoid human-chosen passwords. Generate a random 256-bit key:
   ```bash
   # Using OpenSSL:
   openssl rand -hex 32

   # Or using Python:
   python3 -c "import secrets; print(secrets.token_urlsafe(32))"
   ```

2. **Restrict File Permissions (`chmod 600`)**:
   Store the key in `central_service/.env` and lock permissions so that only the service owner/root can read it:
   ```bash
   chmod 600 central_service/.env
   ```

3. **Systemd `EnvironmentFile` Isolation**:
   The systemd service unit (`magnetometer-server.service`) loads `EnvironmentFile=-%WORKING_DIR%/.env`. Systemd injects these variables directly into the process environment in memory, preventing secrets from appearing in process listings (`ps aux`).

## 2. Cloudflare Tunnel Token (`cloudflared`)

### Understanding the Token:
- The Cloudflare Tunnel token generated by Cloudflare Zero Trust is an **ephemeral connector secret** scoped *strictly* to establishing the outbound QUIC reverse tunnel for that specific Tunnel ID.
- It **cannot** be used to log into your Cloudflare dashboard, modify DNS records, or access billing.

### Storage & Protection:
1. **Systemd Root Storage**:
   When you install the tunnel using `sudo cloudflared service install <TOKEN>` (or via `central_service/remote_access.sh`), the token is written to `/etc/cloudflared/config.yml` owned by `root:root` with permissions `0600`.
2. **Named Tunnel Credentials**:
   If configuring named tunnels manually, Cloudflare creates a JSON credentials file `~/.cloudflared/<tunnel-id>.json`. This directory is ignored in `.gitignore` and must never be committed to Git.

## 3. Remote Edge Gateways & Python Clients (`gateway.py`)

For remote Raspberry Pis deployed in the field running `gateway.py`:

1. **Dedicated Client Configuration**:
   Store the server URL and API key in a local `.env` file on the field gateway:
   ```ini
   CENTRAL_SERVER_URL=https://mag.yourdomain.com
   API_KEY=your_secure_random_token
   ```
   Set permissions: `chmod 600 .env`.

2. **Scoped / Per-Site Keys (Multi-Site Deployments)**:
   For fleets of gateways across multiple locations, assign unique API keys per site. If a single field laptop or Pi is lost or compromised, you can revoke only that site's key without needing to re-provision the rest of the fleet.

## 4. Embedded Microcontrollers (ESP32 Sensor Nodes & Receivers)

Microcontrollers in the field are physically exposed, making secret storage a distinct challenge.

```
+-------------------------------------------------------------------------------+
| ESP32 Secrets Storage Hierarchy                                              |
|                                                                               |
| Level 1: Hardcoded #define (Avoid)   --> Secrets baked into compiled binary   |
| Level 2: Dynamic NVS (Recommended)  --> Flashed via USB CLI; no code secrets |
| Level 3: NVS + Flash Encryption     --> Hardware AES key burned in eFuses    |
+-------------------------------------------------------------------------------+
```

### Level 1: Avoid Hardcoding Credentials in Source Code (Anti-Pattern)
- **Do NOT** define Wi-Fi passwords or API keys in `#define` macros or C++ source files.
- Hardcoded strings are easily leaked via public Git commits or extracted from `.bin` firmware dumps using string inspection tools.

### Level 2: Dynamic NVS Storage (Current System Architecture)
- Firmware source code contains **zero credentials**.
- Nodes boot in unprovisioned mode until configured.
- Credentials (`WIFI_SSID`, `WIFI_PASS`, `TARGET_IP`, `API_KEY`) are injected over USB UART using `scripts/provision_node.py` or the interactive Serial CLI (`WIFI <ssid> <pass>`, `TARGET <ip> <port>`).
- Credentials are saved in the ESP32's internal **Non-Volatile Storage (NVS)** partition in flash memory.

### Level 3: Hardware Flash & NVS Encryption (High-Security Outdoor Deployments)
If sensor nodes are deployed in unattended outdoor or public locations where physical theft is a possibility:
- **ESP32-S3 and ESP32-C6** support **Hardware Flash Encryption (AES-XTS-256)** and **NVS Encryption**.
- An encryption key is generated and burned into write-protected hardware **eFuses** (`BLOCK_KEY0`).
- Even if an attacker physically desolders the SPI flash chip and reads it with an external programmer, all NVS contents (Wi-Fi passwords and API keys) appear as encrypted pseudorandom data.

## 5. Git Hygiene & Leak Prevention

| Practice | Details |
| :--- | :--- |
| **Strict `.gitignore`** | `.env`, `.env.*`, `*.cfg`, `provision_config.json`, `provision_receiver_config.json`, `.cloudflared/`, and `*.token` are strictly ignored. |
| **Commit Only Template Files** | Always commit template files with placeholders (e.g. `central_service/.env.example`, `provision_config.example.json`, `provision_receiver_config.example.json`). |
| **Pre-Commit Scanners** | For shared/public repositories, install `git-secrets` or `trufflehog` to scan for high-entropy strings and block accidental commits containing credentials. |
